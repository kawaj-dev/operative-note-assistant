# Operative Note Assistant v0.1

**オペレコ作成支援アプリ — 必要な情報を、漏れなく、書きやすく —**

## 概要

Operative Note Assistantは、手術記録（オペレコ）の作成を支援するWebアプリです。

手術記録は、症例ごとに記載内容が異なり、医師によって記載方法にもばらつきが生じるため、必要な情報が抜けていたり、自由記載の中から必要な情報を読み取る必要が生じたりすることがあります。

本アプリでは、入力画面そのものが「何を記録する必要があるか」を示し、手術記録の作成を支援する仕組みを目指しています。

症例ごとに入力が必要となる項目をスムーズに記録できるようにし、術中経過や手術所見など、症例ごとに内容が異なる情報は自由記載として残します。

記録者が「何を書くべきか」をすべて記憶して文章を作成するのではなく、画面に沿って必要な情報を確認しながら記録できるようにすることで、必要な情報の記載漏れや記載方法のばらつきを減らし、手術記録の作成負担を軽減することを目指しています。

v0.1では呼吸器外科の架空症例を題材に、手術記録の作成・下書き保存・再開・完成保存・症例一覧・詳細表示までを実装しています。

> 本アプリは学習・ポートフォリオ目的のプロトタイプです。実際の診療には使用できません。

---

## 開発背景

手術記録には、手術日、術式、手術時間、出血量など、一定の形式で記録しやすい情報がある一方、手術所見や術中経過など、症例ごとに内容が異なる情報もあります。

すべてを自由記載にすると、記録者が必要な項目を把握した上で文章を作成する必要があります。また、後から必要な情報を確認するときにも、文章の中から該当する情報を探す必要があります。

一方で、すべてを定型項目にするだけでは、症例ごとの違いや手術中に起きたことを十分に記録できません。

そこで本アプリでは、

**「構造化できる情報は入力項目として整理し、症例ごとに異なる情報は自由記載として残す」**

という考え方を基本としました。

さらに、単に入力欄を並べるのではなく、

**「入力画面そのものが、何を記録する必要があるかを示す」**

ことを、このアプリの中心的な考え方としています。

## 医療情報を扱う上での設計方針

本アプリは学習・ポートフォリオ目的のプロトタイプですが、医療情報を扱うシステムを想定する上で、**必要以上に情報を収集・保存・出力しないこと**を設計上の前提としています。

そのため、v0.1では本アプリの目的に必要のない患者個人情報の入力項目を設けていません。

また、入力したデータを外部API・AIサービスへ送信する機能や、CSV・Excel等のファイルとして出力する機能も設けていません。

これらの機能が必要となる場合には、単に便利な機能として追加するのではなく、

- 利用目的
- 対象となる情報
- アクセス権限
- 保存方法
- 受け渡し方法
- 外部サービスへ送信する必要性

などを整理した上で実装を検討する必要があると考えています。

## 個人情報保護と守秘義務

**本プロジェクトでは、実在する患者・症例・手術記録のデータは一切使用していません。**

使用している症例データは、すべて本アプリの機能検証のためにゼロから作成した架空のデモデータです。

実在する医療情報を匿名化・加工したデータも使用しておらず、本アプリの目的に不要な患者個人情報を入力・保存する項目も設けていません。

ポートフォリオとして公開するにあたり、以下の方針でデータを管理しています。

- 症例IDを `DEMO-001` 形式に制限
- 術者・助手等は架空の選択肢のみ使用
- 画面上に実在情報の入力禁止を表示
- 本アプリの目的に不要な患者個人情報の入力項目を設けない
- SQLite DBをGit管理対象から除外
- `.env`、仮想環境、キャッシュ等をGit管理対象から除外
- 秘密情報・認証情報をコードに保持しない
- HTML出力時のエスケープを行う
- CSV・Excel出力を実装しない
- 外部API・AIサービスへの医療情報送信を実装しない

自由記載欄には任意の文字列を入力できるため、実在情報を自動的に検出・匿名化する機能はありません。

また、本アプリには実運用を想定した認証・権限管理、監査ログ、DB暗号化、バックアップ等は実装していません。

そのため、**実際の医療情報を扱う用途には使用できません。**

## このアプリで目指すこと

Operative Note Assistantが目指しているのは、医学的な判断を自動化することではありません。

手術内容をアプリが判断したり、術式や処理方法を推奨したりするのではなく、**記録する人が必要な情報を確認しながら、スムーズに手術記録を作成できる環境をつくること**を目的としています。

v0.1では、以下を重視しています。

- 必要な情報を画面に沿って順番に確認できること
- 構造化できる情報は選択式や入力項目として整理すること
- 症例ごとの差を自由記載として残せること
- 不要な項目まで一律に入力させないこと
- 入力途中で中断しても、保存済みの内容から再開できること
- 医学的な判断や処理方法をアプリ側で決定しないこと

v0.1は網羅的な医療システムを目指すものではなく、**オペレコ作成を支援する入力方法そのものを検証するためのプロトタイプ**として開発しています。

## 入力設計

本アプリでは、情報の性質に応じて入力方法を分けています。

### 構造化できる情報

術式、体位、リンパ節郭清、手術時間など、一定の形式で整理できる情報については、選択式や専用の入力項目を使用します。

これにより、自由文だけに依存せず、必要な情報を確認しながら記録できるようにしています。

### 症例ごとに異なる情報

手術所見、術中経過、各処理の詳細など、症例によって内容が異なる情報については自由記載を残します。

定型化すること自体を目的とせず、**構造化に向いている情報と自由記載に向いている情報を分ける**ことを重視しています。

### 条件に応じた入力

すべての症例に同じ入力欄を表示するのではなく、選択した内容に応じて必要な項目を表示します。

たとえば「合併切除なし」の場合には合併切除箇所の入力を求めないなど、不要な入力を減らしながら必要な情報を確認できるようにしています。

---

## 入力途中の保存と再開

手術記録の作成中に別の対応などで入力を中断する場面を想定し、完成時の保存だけでなく、入力途中の内容を**下書き**として保存できます。

入力内容を変更すると、約1秒後に自動的に下書き保存を行います。画面には保存状態と保存時刻を表示します。

また、自動保存とは別に、各ステップから「下書き保存」を実行することもできます。

下書きでは必須項目が未入力でも保存でき、症例一覧から再度開いて入力を続けることができます。

完成保存時には必要な項目を検証し、

- 下書き（draft）
- 完成（completed）

を区別して管理します。

これにより、**入力途中で中断した場合にも、それまでの記録を失いにくくし、続きから作成できること**を目指しています。

## 画面フロー

v0.1では、入力内容を10のステップに分けています。

| Step | 内容 |
| --- | --- |
| 01 | 基本情報・開始／終了時刻・手術時間 |
| 02 | 手術担当（複数の術者・助手、麻酔） |
| 03 | アプローチ |
| 04 | 術式詳細・体位・条件付き切除肺葉 |
| 05 | リンパ節郭清 |
| 06 | 合併切除 |
| 07 | 出血量・輸血 |
| 08 | 手術図 |
| 09 | 手術所見・手術経過 |
| 10 | 内容確認・完成保存 |

上部のステップから前後の入力画面へ移動できます。

## 手術図

手術記録では、文章だけでは表しにくい位置関係や手術操作を図として記録することがあります。

本アプリでも、手術に関する情報を図上に記録するための手術図機能を試作しています。

ただし、アプリが手術図を自動的に完成させたり、図から解剖や術式を判断したりすることは目的としていません。

基本的な考え方は、

**「アプリが手術図を完成させるのではなく、記録者が必要な情報を図として残すための入力環境を用意する」**

ことです。

### 現在の状態

手術図については、SVGを使用した描画・保存・再表示の基本機能を実装しています。

一方で、ベースとなる図や入力画面の構成については、より直感的に記録できる形へ見直すため、**現在再設計中です**。

そのため、現在の手術図UIおよびベース図を最終仕様とはしていません。

解剖図等を今後使用する場合には、出典・ライセンス・対象となる解剖・医学的な妥当性を確認した上で採用します。

## データベース

SQLiteを使用しています。

v0.1では必要以上にテーブルを細分化せず、以下の3テーブルを使用しています。

| テーブル | 用途 |
| --- | --- |
| `operative_notes` | 手術記録の入力内容・下書き／完成状態等 |
| `operative_diagrams` | 手術図ごとの状態 |
| `diagram_objects` | 手術図上に配置したオブジェクト |

術者・助手・リンパ節などの複数値はJSON配列として保存します。

入力内容の一部にもJSONを使用し、v0.1で不要なテーブル分割を避けています。

手術図と図上のオブジェクトは構造化データとして保存し、再表示できる構成としています。

## 安全性と制限事項

入力値の検証、Jinja2の自動エスケープ、SQLプレースホルダー、CSRF対策等を使用し、入力内容をそのままHTMLやSQLとして扱わないようにしています。

一方、v0.1はローカル環境での学習・機能検証を目的としたプロトタイプであり、以下は対象外です。

- 実際の患者情報の保存
- 認証・権限管理
- 実運用向け監査ログ
- DB暗号化
- バックアップ
- 完成後の記録編集
- 電子カルテ連携
- NCD連携
- CSV・Excel出力
- 外部API・AIサービスへの医療情報送信
- 医学的判断
- 術式・処理方法の推奨
- AIによる解剖認識
- AIによる手術図生成

本アプリはローカル環境での機能検証を前提としており、実際の医療情報や秘密情報を保存しないでください。

## 今後の課題

v0.1は、オペレコ作成支援という考え方を検証するためのプロトタイプです。

今後は、実装範囲を無理に広げるのではなく、実際に画面を操作しながら必要性を確認し、要件を整理した上で段階的に改善していきます。

現在の主な検討事項は、**Step 08「手術図」の再設計**です。

現在の手術図は機能検証としてSVGによる描画・保存・復元まで実装していますが、「何を入力する画面なのか」がより直感的に伝わるUIとするため、入力内容、ベース図、操作方法を改めて検討しています。

術式ごとの入力項目についても、v0.1で網羅するのではなく、必要性と根拠を確認しながら段階的に検討します。

## 開発方針

このプロジェクトでは、最初から完成形を決めてすべてを実装するのではなく、

**小さく作る → 実際に操作する → 必要な機能を考える → 要件を整理する → 改善する**

という流れで開発しています。

実際に画面を操作する中で、入力項目の配置、複数入力、条件付き表示、入力途中の保存・再開などの必要性を確認し、v0.1の仕様を段階的に見直してきました。

機能を増やすこと自体を目的とせず、**なぜその機能が必要なのかを考えた上で実装すること**を、このプロジェクトの開発方針としています。
